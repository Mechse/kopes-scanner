L155: 
L156: A host is active if its agent has checked in within your stale-host threshold (default: 30 days). Hosts that stop reporting beyond the threshold are excluded from your billable count automatically. You can adjust the threshold per account.

L221: # PatchMon
L222: 
L223: ### Enterprise-grade Linux patch & server management platform
L224: 
L225: * * *
L226: ## What is PatchMon?
L227: 
L228: PatchMon is an enterprise-grade platform that gives operations teams a single pane of glass to monitor, patch and secure their Linux fleet, with FreeBSD and Windows agent support.
L229: 
L230: A lightweight agent communicates outbound-only to the PatchMon server on your schedule - no inbound ports required on monitored hosts - delivering real-time visibility into package health, compliance posture and system status across environments of any scale.
L231: 
L232: * * *
L233: ## Why PatchMon?
L234:   * Outbound-only agents - no inbound firewall changes, no SSH or WinRM exposure, no VPN required.
L235:   * Single binary, bundled UI - one Go binary with the React frontend embedded. One container, no Node runtime at deploy time.
L236:   * Open source, with a managed cloud - AGPL v3 licensed, free to self-host. Production hosting available at 【116†patchmon.net/cloud†patchmon.net】.
L237:   * Multi-OS by design - Linux (apt, dnf, yum, apk, pacman), FreeBSD (pkg) and Windows, handled by the same agent and control plane.
L238: * * *
L239: ## Quick Start
L240: 
L241: Docker is the fastest way to try PatchMon:
L242: 
L243:     mkdir patchmon && cd patchmon
L244:     bash -c "$(curl -fsSL https://raw.githubusercontent.com/PatchMon/PatchMon/refs/heads/main/docker/setup-env.sh)"
L245:     docker compose up -d
L246: 
L247: Open `http://localhost:3000`, create an admin user, add a host in the UI and copy the generated install command onto the target server.
L248: 
L249: Full deployment options (Docker manual, Proxmox LXC, PatchMon Cloud) are in the 【117†Deployment】 section.

L252: ## Features at a Glance
L253: ### Patch Management
L254: 
L255: The core of PatchMon - orchestrate updates across your fleet with validation, approval and live visibility.
L256: Capability  | What It Does
L257: --- | ---
L258: Dry-Run Validation  | Preview the exact package transaction on a host before anything touches production. Every run captures the full plan so you know what would change.
L259: Approve & Execute  | One-click approval turns a validated dry-run into a real patch run, with a per-host audit trail of who approved what and when.
L260: Scheduled Patching  | Patch policies decide when updates apply - immediate, maintenance window or delayed rollout. Approve now, execute later.
L261: Live Patch Streaming  | Watch patch execution in real time from the browser. Agent stdout/stderr is streamed over WebSocket, with the ability to stop a run mid-flight.
L262: Selective Patching  | Target specific packages, security-only updates or a full upgrade. Works across apt, dnf, yum, apk, pacman and FreeBSD pkg.
L263: Patch History & Audit  | Full searchable history of every run - exit code, duration, packages touched, approver and host.

L266: --- | ---

L269: Package Inventory  | View every installed package across your fleet, filter to outdated or vulnerable ones, and see exactly which hosts need attention.
L270: Repository Tracking  | Every APT / YUM / DNF / APK / pacman repository configured on each host, in one place.
L271: Docker Monitoring  | Automatic discovery of containers, images, volumes and networks with real-time status pushed over WebSocket.

L154: ## Patch image vulnerabilities
L155: 
L156: 【71†Section titled “Patch image vulnerabilities”】
L157: 
L158: Arcane can patch fixable OS-package vulnerabilities with 【86†Copacetic†project-copacetic.github.io】 (copa), an image patching tool, instead of waiting for the image’s publisher to release a fixed version.
L159:   1. Open Security → Patches. The table lists scanned images with their fixable CVE counts, last scan time, last patch status, and patched tag.
L160:   2. Click Patch on a row. You can also patch from the image detail page or the Images table row menu.
L161:   3. Follow progress in the Activity Center. Patches run in the background, one at a time, and need the `images:patch` permission.
L162:   4. Redeploy your containers against the new tag to use the patched image.
L163: 
L164: What happens during a patch:
L165:   * Arcane runs copa against the Docker daemon’s built-in BuildKit (Docker’s image build engine). No helper container is started, and Arcane’s stored registry credentials are used to pull.
L166:   * If the image’s latest scan has a stored report, only the vulnerabilities in that report are patched. Without one, copa updates every outdated OS package in the image.
L167:   * The result is tagged with a suffix, so `nginx:1.25` becomes `nginx:1.25-patched` by default. It exists only in the local Docker daemon. Nothing is pushed, and running containers are not touched.
L168:   * Arcane re-scans the patched image afterwards, and the Patches table shows the result.
L169: What can’t be patched:
L170: 
L171:   * Vulnerabilities in language or application dependencies (npm, pip, Go modules, and so on). Only OS packages are patched; rebuild the image for the rest.
L172:   * Locally built images with no registry source. Rebuild them instead.
L173:   * Untagged images.
L174: ### Schedule patching
L175: 
L176: 【72†Section titled “Schedule patching”】
L177: 
L178: Turn on Scheduled Image Patching under Environments → your environment → Security → Image Patching, and set the patch job’s schedule in Automations. The default `0 0 3 * * *` runs daily at 03:00. Each run patches scanned images in the local Docker environment that have a stored report and haven’t been patched since their latest scan.
L179: ## Configure scans
L180: 
L181: 【73†Section titled “Configure scans”】
L182: 
L183: Scan settings live under Environments → your environment → Security → Vulnerability Scanning and apply to every scan in that environment. Run a new scan to refresh saved results after changing them.
L184:   * Only Report Fixable Vulnerabilities records only vulnerabilities that have a known fixed version.
L185:   * Trivy Config (YAML) takes the contents of a `trivy.yaml` file.
L186:   * .trivyignore takes one vulnerability ID per line. Lines starting with `#` are comments.
L187: 
L188: Options Arcane passes on the command line win over the YAML: output format, timeout, cache directory, database or server settings, exit code, and the fixable-only setting.
L189: CPU Limit (cores), Memory Limit (MB), and Concurrent Scan Containers cap the resources scans use; see 【82†Settings】.
L190: ### Use a remote Trivy server
L191: 
L192: 【74†Section titled “Use a remote Trivy server”】
L193: 
L194: Trivy can run as a server that holds the vulnerability database, so Arcane doesn’t have to download and load it on each host. This helps on small or 32-bit hosts, especially armv7, where the local database may fail to load.
L195: 
L196:   1. Turn on Use Remote Trivy Server.
L197:   2. Set Trivy Server URL, for example `http://trivy.example.com:4954`.
L198:   3. Optional: set Trivy Server Token if the server requires authentication.
L199: Scan containers must be able to reach the server URL; Trivy Network controls their network. Arcane passes the token in the `TRIVY_TOKEN` environment variable, so it doesn’t show up in process arguments.
